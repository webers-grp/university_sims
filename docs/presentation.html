Background & Motivation

The Challenge of Modern Academic Administration

Traditional institutional silos lead to data duplication, grade tampering vulnerabilities, and delayed fee reconciliation.

Legacy Operational Bottlenecks
  • Data Redundancy & Anomalies: Student records duplicated across departments causing update and deletion conflicts.
  • Integrity Violations: Exam marks manually entered without boundary constraints (risk of out-of-bounds scores > 100 or < 0).
  • Fee Reconciliation Lag: Finance offices operating independently from academic registries, resulting in delayed exam permits.
  • Security Deficits: No database-level Role-Based Access Control (RBAC), exposing raw tables to unauthorized modifications.
UniSIMS Solution & Design Goals
  • Strict 3NF Schema: Exactly 7 relational entities eliminating all insertion, update, and deletion anomalies.
  • Engine-Enforced Rules: Database triggers and stored procedures enforce validation before commits reach disk.
  • Instant Financial Ledger Sync: Auto-calculating views (`vw_StudentFeeBalances`) calculating real-time arrears in KSh.
  • Enterprise Recovery: Automated hot backup and disaster recovery pipelines verifying 100% data fidelity.

Relational Theory

Normalization Proof: 0NF → 1NF → 2NF → 3NF

Rigorous mathematical decomposition eliminating redundancy, update anomalies, and non-key dependencies.

0NF Unnormalized

Single flat table with repeating course arrays, multi-valued exam marks, and duplicated department head details.

Student(ID, Name, [Courses], Dept, Head, [Marks])

Severe update & insertion anomalies.

1NF Atomic Values

Eliminated all repeating groups. Every attribute contains strictly atomic, indivisible scalar values.

Defined primary keys across all flattened entities.

Primary keys assigned, but partial dependencies remained.

2NF No Partial Deps

Every non-prime attribute is fully functionally dependent on the whole candidate key, not a subset.

Decomposed composite keys in Registrations and Examinations.

Partial dependencies fully eliminated.

3NF Zero Transitive

Non-key attributes depend strictly and solely on the primary key ($X \to Y$, where $X$ is a superkey).

7 Distinct entities linked exclusively by Foreign Keys.

Formal 3NF achieved with zero anomalies.

Advanced Database Feature 1

Active Database Triggers: Boundary Integrity

Engine-level enforcement that intercepts corrupt data before disk persistence, independent of application code.

Trigger 1: trg_CheckExamMarksBoundary

Guarantees that no instructor or external API can persist illegal exam scores (e.g. -15 or 125 marks).

DELIMITER $$
CREATE TRIGGER trg_CheckExamMarksBoundary
BEFORE INSERT ON examinations
FOR EACH ROW
BEGIN
  IF NEW.marks_obtained < 0 OR NEW.marks_obtained > 100 THEN
    SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'Exam marks must be between 0 and 100';
  END IF;
END$$

Tested and verified in the ADBMS Lab with instant exception catch.

Trigger 2: trg_UpdateRegistrationStatus

Maintains academic lifecycle state automatically whenever grades are finalized.

DELIMITER $$
CREATE TRIGGER trg_UpdateRegistrationStatus
AFTER INSERT ON examinations
FOR EACH ROW
BEGIN
  UPDATE registrations
  SET status = 'completed'
  WHERE registration_id = NEW.registration_id;
END$$

Automates multi-table state synchronization with zero manual intervention.

Advanced Database Feature 5

Database Security & Role-Based Access (RBAC)

Enforcing the Principle of Least Privilege directly at the MariaDB grant table level.

Role 1 admin_role

Full Administrative & Configuration Authority

  • ALL PRIVILEGES across university_sims.*
  • Can execute DDL (CREATE, ALTER, DROP).
  • Manages user account creation and role assignment.
  • Executes master backup and restore procedures.
  • Full access to fee payment ledgers.
Role 2 lecturer_role

Restricted Academic Grading Authority

  • SELECT only on students, courses, departments, registrations.
  • SELECT, INSERT, UPDATE strictly on examinations.
  • NO ACCESS to fee_payments (financial isolation).
  • NO DDL privileges (cannot alter schemas or drop tables).
SQL Grant Command: GRANT SELECT ON university_sims.students TO 'lecturer_role';  |  Enforces institutional data governance compliance.

Top 10 Examiner Questions & Winning Technical Answers

1. Why is 3NF necessary for this system? Could 2NF have been enough?
2NF only eliminates partial functional dependencies (where a non-key attribute depends on part of a composite key). It does NOT eliminate transitive dependencies (where a non-key attribute depends on another non-key attribute). In 2NF, storing department_name or tuition_fee inside the student table would cause transitive dependencies (student_id → course_id → department_name). Updating a department name would require updating every student record. 3NF removes all transitive dependencies by decomposing them into separate entities linked by foreign keys.
2. How does the database guarantee that exam marks cannot exceed 100 or drop below 0?
We implemented trg_CheckExamMarksBoundary as a BEFORE INSERT and BEFORE UPDATE trigger on the examinations table. If NEW.marks_obtained < 0 OR NEW.marks_obtained > 100, the engine calls SIGNAL SQLSTATE '45000'. This aborts the query immediately at the database kernel level, rolling back the transaction even if an external application tries to bypass validation.
3. How does your fee calculation guarantee precision and avoid rounding errors?
All currency values are strictly typed as DECIMAL(10,2) rather than FLOAT or DOUBLE to prevent IEEE 754 floating-point inaccuracies. The relational view vw_StudentFeeBalances computes arrears dynamically by taking courses.tuition_fee - COALESCE(SUM(fee_payments.amount_paid), 0) grouped by student. This guarantees that student arrears are always mathematically exact.
4. Why did you create B-Tree composite indexes instead of single-column indexes?
Queries in student portals typically filter by multiple fields simultaneously, such as WHERE course_id = ? AND status = 'active'. A single-column index on course_id would still require scanning all rows for status. The composite B-Tree index idx_students_course_status (course_id, status) allows MariaDB to locate the exact leaf node in $O(\log n)$ time, eliminating secondary index lookups and full table scans.
5. How does Role-Based Access Control (RBAC) protect academic integrity?
We defined dedicated database roles: admin_role and lecturer_role. Lecturers have SELECT grants on student/course directories and INSERT/UPDATE on examination marks, but have zero access to the fee_payments table and no DDL privileges. Even if a lecturer's credentials are compromised, an attacker cannot delete tables, alter tuition fee amounts, or modify course structures.
6. What happens if a student is deleted? How is referential integrity preserved?
Foreign keys on registrations and examinations specify ON DELETE CASCADE, ensuring that deleting a test student cleans up associated registration and grading rows automatically. However, fee_payments ledgers use RESTRICT or soft archival to guarantee that financial audit trails cannot be accidentally wiped.
7. What is the difference between a Stored Procedure and a Relational View?
A view is a virtual table representing a pre-defined SELECT query without taking arguments; it is used for simplifying reads and reporting (e.g. vw_StudentFeeBalances). A stored procedure is a compiled executable routine that accepts input/output parameters, contains procedural logic (IF/ELSE, loops, transactions), and can perform data modification operations (INSERT, UPDATE, DELETE) atomically on the server.
8. How do you prove that the UI is in real-time sync with the database?
The PHP backend does not use local JSON caching or static session storage. Every page request queries MariaDB live via PDO prepared statements. Any record inserted or edited directly in phpMyAdmin or the MariaDB CLI reflects immediately on the UI upon the next page refresh, and vice versa.
9. How does your backup script prevent table locking during operations?
In 04_backup_recovery.sh, mysqldump runs with the --single-transaction flag. Because all tables use the InnoDB storage engine, this creates a read-consistent snapshot using Multi-Version Concurrency Control (MVCC) without acquiring table locks, allowing students and staff to continue writing without downtime.
10. If an examiner asks: 'Can you show me your EXPLAIN query plan right now?'
Navigate to the ADBMS Lab (advanced_demo.php) → Query Plan section. Click 'Run EXPLAIN Plan'. The output displays type: ref, key: idx_students_course_status, and rows: 1-3, proving that the MariaDB optimizer chooses our B-Tree composite index over a full table scan.
